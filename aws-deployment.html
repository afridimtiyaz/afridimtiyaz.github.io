Project overview

Log360 can be installed on an Amazon EC2 instance to collect and analyze logs from AWS services, EC2 instances, and on-premises systems, and to archive logs to Amazon S3 for long-term retention.

I wrote the help page that explains this deployment end to end: planning resources, creating the EC2 instance, connecting it to log sources, installing the product, configuring S3 archiving, onboarding log sources, and verifying that everything works.

Documentation challenge

A cloud deployment sits between two systems. Administrators work in the AWS Management Console to create and network the instance, and in Log360 to install the product and add log sources. Some readers know AWS well but not Log360; others know Log360 but are new to AWS.

Much of the related information, such as installation steps, system requirements, ports, and agent setup, already existed on other pages. The challenge was to cover everything specific to AWS without repeating those pages or letting them drift out of sync.

Page structure

The page follows the order in which an administrator actually deploys the product.

  1. OverviewWhat the deployment does and what it includes.
  2. PrerequisitesInstance, network, security groups, IAM credentials, storage, and S3 bucket to have ready.
  3. Plan your deploymentArchitecture, instance sizing by log volume, storage, AWS licensing, and log source connectivity.
  4. Set up the AWS environmentCreate the EC2 instance and configure network connectivity.
  5. Set up Log360 on the EC2 instanceInstall the product, linking to the standard installation guide.
  6. Configure log archiving to Amazon S3Keep active data on SSD and use S3 for archives only.
  7. Onboard log sourcesAdd AWS services, EC2 instances through agents, and on-premises sources.
  8. Verify the deploymentCheck console access, log collection, and S3 archiving.

Architecture diagram

I included a deployment diagram so readers can see where each component sits before they start configuring it. It shows logs flowing into the Log360 server from three directions, and archived logs flowing out to S3.

Writing decisions

The choices that shaped the page, and why I made them.

Follow the deployer's order

Each section matches the next thing an administrator does, from planning to verification, so the page can be followed top to bottom during a real deployment.

Link instead of repeating

Installation, system requirements, ports, and agent setup already had their own pages. I stated what applies and linked to them, so updates happen in one place.

The standard Log360 installation procedure applies when installing the product on an EC2 instance.

Put decisions before steps

Sizing the instance is the choice that is hardest to undo, so the planning section comes before any setup steps and gives a clear rule for when a single node is enough.

Warn where mistakes are costly

I called out the errors most likely to cause problems later, such as storing search indexes in S3 or pointing agents at an address they cannot reach.

Do not use Amazon S3 for active search indexes.

Match the AWS console

Steps use the exact labels administrators see in the AWS Management Console, such as Launch instance and Application and OS Images (AMI), so readers never have to guess where to click.

End with a way to check

The page closes with a verification checklist, so administrators know when the deployment is complete instead of assuming it is.

Set up the AWS environment

Create an EC2 instance

  1. Sign in to the AWS Management Console and open the EC2 dashboard.
  2. Select the AWS Region in which you want to deploy the product.
  3. Click Launch instance.
  4. Enter a name for the EC2 instance.
  5. Under Application and OS Images (AMI), select a supported operating system for the product.
  6. Under Instance type, select an instance type that meets the CPU and memory requirements specified in the system requirements.
  7. Configure a key pair for secure access to the EC2 instance.
  8. Under Network settings, select the VPC and subnet that provide connectivity to the log sources that you want to monitor.
  9. Configure the security group to allow the ports required for accessing the product and collecting logs.
  10. Under Configure storage, attach SSD-backed storage that meets the product's storage requirements.
  11. Review the configuration and click Launch instance.
Verify the deployment

Verify log collection

Check that:

  • AWS cloud sources are connected successfully.
  • Logs from AWS EC2 instances are being collected.
  • Agent-based sources are communicating with the product server.
  • On-premises sources can send logs to the EC2 instance.
  • Logs are appearing in the product console.
